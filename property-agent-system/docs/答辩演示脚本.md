# 答辩演示脚本（5 分钟版）

> 目标：在 5 分钟内讲清“问题 → 方案 → 系统演示 → 数据与评估 → 创新点”，重点展示多智能体闭环，而不是聊天机器人。

## 0. 开场（20 秒）

“各位老师好，我的课题是《基于多智能体协同的物业报修工单自动派发与闭环验证系统》。传统物业报修靠人工接单、人工判断、人工派单，紧急工单容易混在一起，处理过程不透明，完成后也缺少自动验收。我的系统用 4 个 Agent 加 1 个协调器，把一条工单从理解、派单、监控到验收全部自动流转，并且每一步决策都可追溯。”

## 1. 系统总览（40 秒）

打开首页 `http://127.0.0.1:8000`：

- 左侧是 6 个模块：总览、工单中心、智能派单、决策日志、数据分析、系统架构。
- 总览上方是 3000 条历史工单的核心指标：闭环率 93.6%、超时率 12.1%、平均处理 92.9 分钟、自动派单准确率 98.8%。
- 中间 30 天趋势、类型分布、楼栋排名；右侧是最新工单和 Agent 运行指标。
- 说明：看板数据不是写死的，来自 `reports/analysis_summary.json` 与实时 SQLite。

## 2. 核心演示：一条工单的完整闭环（120 秒）

点击「智能派单」→ 右侧「运行完整闭环演示」。

按时间线讲解（页面会自动逐条播放）：

1. **T+00 报修理解**：业主提交“5栋1单元水管爆裂，楼道积水，水已经流到电梯口”。理解 Agent 识别：给排水 / 水管爆裂 / 5栋1单元 / 紧急 / 30 分钟，置信度 0.92。
2. **T+00 派单决策**：按“主工种优先 + 六因子评分”选水电工王建国，P0，30 分钟截止；可以展开候选得分，说明为什么不是赵磊。
3. **T+25 接单超时**：工单一直未接单，监控 Agent 生成 L1 提醒“超过接单时限 15 分钟”。
4. **T+26 接单**：王建国接单，工单进入处理中（接单响应 26 分钟，超时）。
5. **T+35 处理超时**：超过 30 分钟时限仍未完工，监控 Agent 升级物业主管，工单标记 escalated。
6. **T+38 验收退回**：维修工提交“已更换阀门”，但照片 0 张。闭环验证 Agent 检查 5 项规则，发现“现场照片齐全”未满足，状态变为退回整改。
7. **T+45 补充材料**：上传 2 张照片 + 完整处理记录，再次验收；处理说明、照片、完工时间、内容匹配全部通过，状态关闭，工单闭环。
8. **看板刷新**：实时超时 +1、已闭环 +1，闭环验证通过率与超时率同步变化。

强调：这不是预设动画，演示调用的是真实 `POST /api/demo/run`，所有事件、Agent 日志和预警都写入数据库，刷新后仍可查。

## 3. 工单中心与决策日志（50 秒）

- 打开「工单中心」，展示 8 条实时演示工单：待接单、处理中、退回整改、已闭环。
- 点开任意一条，右侧抽屉展示：
  - 生命周期事件时间线（谁在什么时候做了什么）；
  - 每个 Agent 的 rationale、confidence、耗时；
  - 预警记录与升级对象。
- 打开「决策日志」，按 Agent 过滤。举例：
  - 派单日志里能看到候选维修工每一项得分；
  - 验收日志里能看到 5 项检查逐项通过/失败；
  - 所有日志记录 trace_id，可关联到同一条工单。
- 说明人工接管：工单中心支持改派，改派会重置时限并记录 `human_takeover`，避免系统黑箱。

## 4. 数据分析与评估（50 秒）

打开「数据分析」：

- 给排水类工单占 32.1%，是主要风险源；工作日 8–11 点、18–21 点双高峰。
- 超时工单闭环率仅 57.5%，非超时 98.5%，说明超时治理是闭环关键。
- 维修工效率排名、楼栋超时率排名。
- 这套分析不是摆设：`dispatch_priors.json` 中的类型时长、维修工准时率直接进入派单评分。
- 打开「API 评估」或报告：600 条样本上，类型理解 98.83%、紧急度 96.50%、工种匹配 99.17%、综合派单 98.83%、验收通过 71.33%、人工改派 5.30%。验收通过率偏低是因为历史记录中 16.7% 无照片、15% 说明不匹配，恰好证明验收规则有效。

## 5. 创新点与总结（40 秒）

三个创新点：

1. **多智能体协同闭环**：不是单点分类，而是覆盖理解—派单—监控—验收，验收不通过可退回再闭环。
2. **可追溯决策日志**：每次分类、评分、预警、验收都有依据、置信度和耗时，可解释、可审计。
3. **离线分析反哺在线 Agent**：3000 条历史工单的统计特征形成先验，参与在线派单评分和 SLA 判断，体现大数据专业底色。

“系统目前是单机演示版，使用 SQLite 和可解释规则；后续可接入 LLM 做语义兜底、接入定时任务做常驻监控、替换 PostgreSQL 做生产化。我的汇报完毕，谢谢各位老师。”

## 附：常见提问与回答

**Q1：为什么不用 LangGraph / 大模型？**  
A：本课题重点在工单闭环与可追溯，不在框架复杂度。自研状态机只有几百行，状态迁移、日志、时间注入都可控，部署零外部依赖；理解 Agent 采用可解释规则 + 关键词加权分类，答辩时能逐条解释依据。后续可把 LLM 作为兜底分类器，规则层继续做安全校验。

**Q2：自动派单准确率 98.8% 是否过高？**  
A：评估数据由同一业务规则生成，属于同分布测试，指标偏乐观；真实上线需用脱敏生产工单做外部验证，并以人工改派率持续校准。报告中也明确写了这一局限。

**Q3：验收通过率为什么只有 71%？**  
A：因为历史工单中约 16.7% 没有现场照片、15% 处理说明与报修类型不匹配、部分说明不足 8 字。验收 Agent 按规则退回整改，这正是闭环验证的价值；补充材料后重新验收即可通过。

**Q4：超时预警怎么触发？**  
A：当前通过页面刷新、`POST /api/monitor/scan` 或演示脚本触发巡检；生产环境换成 APScheduler/Celery 每分钟巡检即可，Agent 逻辑不变。

**Q5：数据是真实的吗？**  
A：是模拟数据，固定随机种子 20261020，覆盖 13 类报修、12 名维修工、5 个小区、180 天；生成规则参考真实物业业务，报告中明确说明数据性质，不涉及真实业主隐私。

**Q6：系统如何保证不派错人？**  
A：先用报修类型做工种硬过滤，主工种无人时才启用兜底；再按技能、片区、负载、满意度、准时率、历史时长六因子评分。每一步候选得分都写入决策日志，人工可复核、可改派。
