# 智修云系统设计说明

> 课题：基于多智能体协同的物业报修工单自动派发与闭环验证系统  
> 版本：v1.1.0　技术栈：Python + FastAPI + SQLite + Pandas + 原生 ECharts

---

## 1. 设计目标

传统物业报修流程存在四类问题：描述不规范导致分类慢、紧急与普通工单混杂、派单依赖个人经验、处理过程不透明且缺少自动验收。本系统将一条报修工单拆解为五个可审计的阶段，由专职 Agent 分别负责，协调器负责状态流转与留痕：

1. **理解**：把业主口语文本转成结构化字段（类型、设施、位置、紧急度、SLA）。
2. **派单**：结合技能、片区、负载、历史绩效选择责任人和完成时限。
3. **监控**：对在途工单巡检，接单超时提醒，处理超时升级。
4. **验收**：检查处理说明、照片、时限和安全规则，决定闭环或退回。
5. **分析**：历史工单离线分析反哺派单，看板展示闭环率、超时率、Agent 准确率。

设计原则：**规则可解释、状态可回放、决策可追溯、演示可复现**。

## 3. 核心数据结构

### 3.1 工单 `tickets`

| 字段 | 说明 |
|---|---|
| id / trace_id | 工单号 `WO+日期+流水`；全链路追踪号 `TRC-...` |
| description / reporter_* | 原始报修文本与报修人信息 |
| repair_type / facility_type | 13 类报修类型与 10 类设施 |
| building / unit / room / location | 结构化位置 |
| urgency / urgency_score | 紧急程度与置信分 |
| status | 状态机当前状态 |
| worker_id/name/trade | 责任人信息 |
| priority / sla_minutes / deadline | P0–P3、时限、截止时间 |
| created/understood/assigned/accepted/completed/closed_at | 生命周期时间戳 |
| response_minutes / duration_minutes / is_timeout | 响应与处理时长、超时标记 |
| auto_dispatched / reassigned / escalated / is_demo | 自动派单、人工改派、升级、演示标记 |
| photos_count / result_note | 完工证据 |
| verification_verdict / verification_note | 验收结论 |

### 3.2 事件 `/api/tickets/{id}` 的 `events`

事件类型：`ticket_created`、`understanding_completed`、`ticket_assigned`、`monitoring_alert`、`ticket_escalated`、`ticket_accepted`、`processing_started`、`work_completed`、`verification_passed`、`verification_returned`、`ticket_returned`、`ticket_closed`、`manual_reassign`。每条事件包含 `actor`、`from_status`、`to_status`、`summary`、`detail_json`。

### 3.3 决策日志 `agent_logs`

每条记录：`agent`、`action`、`input_summary`、`output_json`、`rationale`、`confidence`、`duration_ms`、`created_at`。这是答辩时解释“为什么派给张三”“为什么验收不通过”的直接证据。

### 3.4 预警 `warnings`

`level`（L0 即将超时 / L1 接单超时 / L2 处理超时升级）、`warning_type`、`message`、`status`、`escalated_to`。同工单同类型未关闭预警不重复生成。

### 3.5 历史工单 `historical_orders`

3000 条，字段覆盖报修文本、类型、位置、紧急度、维修工、派单方式、响应/处理时长、SLA、超时、闭环、满意度、照片数、处理记录、来源。CSV 与 SQLite 双份，便于 Pandas 离线分析和 SQL 展示。

## 4. Agent 算法细节

### 4.1 报修理解

**分类**：对 13 个类型分别维护正则规则与权重，先做上下文词门控（如电梯类必须出现“电梯/货梯/客梯”），再累加命中权重，取得分最高者；同分按安全优先级排序。未命中任何设施词时归入“其他报修”，并用“水/电”弱线索兜底。

**位置**：正则抽取 `(\d+)[栋号楼幢]`、`(\d+)单元`、`(\d{3,4})[室房]`，支持中文数字；同时识别楼道、大堂、地下车库、天台、卫生间等细节位置。表单提供的位置优先于文本抽取。

**紧急度**：类型基线（燃气/消防/电梯困人为紧急）→ 人员被困/燃气味/火情强制升级 → 大面积/整栋/停水停电提升为高 → 老人儿童孕妇提升为高 → “轻微/不着急”下调。输出 0–1 的 `urgency_score`。

**消防同义词**：除“消防/灭火器/烟感”外，还识别“防火用具、防火门、防火卷帘、消防水带、消防器材、应急灯、疏散指示”等表达，并把“丢失、遗失、不见、被盗、损坏、过期、压力不足、被占用”等视为消防设施失效，避免把“防火用具丢失”误判为其他报修。

**置信度**：关键词强度 + 位置是否抽取成功 + 安全信号，上限 0.98；规则命中与置信度一并写入日志。

**SLA**：类型固定基线；例如电梯困人/水管爆裂 30 分钟、燃气泄漏/消防隐患 15 分钟、电梯/电路故障 60 分钟、普通维修 240–480 分钟。

### 4.2 派单决策

1. 按类型映射主工种，主工种有可用维修工则只在主工种内选择；无可用时才启用备选/综合维修兜底。
2. 对每个候选计算六因子：

```
score = 0.32 × skill_match
      + 0.16 × zone_match
      + 0.20 × (1 - active_tickets/max_daily)
      + 0.12 × rating/5
      + 0.12 × (1 - historical_timeout_rate)
      + 0.08 × historical_speed_score
```

3. 选择综合得分最高者，输出 Top 5 候选及每项得分，按紧急度映射 P0–P3，写入 `deadline = now + sla`。
4. 从 `dispatch_priors.json` 读取类型历史时长 p90、维修工超时率/满意度/平均时长；文件缺失时回退到数据库 `worker_performance()`。
5. 置信度由综合得分和与第二名的分差共同决定。

**设计取舍**：技能是硬约束，片区和负载是软约束；这样既不会把电梯工单派给水电工，又能在高负载时让同片区其他维修工补位。

### 4.3 过程监控

- 接单时限：紧急 10、高 15、中 30、低 60 分钟。超过时限生成 L1 `accept_timeout`，提醒维修工。
- 处理时限：距 deadline 10 分钟生成 L0 `deadline_soon`；超过 deadline 生成 L2 `deadline_timeout`，设置工单 `escalated=1` 并记录升级物业主管事件。
- 预警去重依赖 `warnings(status='open')`；每次巡检写一条监控 Agent 决策日志，包含扫描数量、预警数量、升级数量。
- 生产化可改为 APScheduler 每分钟巡检；当前通过页面刷新、演示脚本与 `POST /api/monitor/scan` 触发，便于测试。

### 4.4 闭环验证

检查分“硬性”和“提示”两类：

| 检查 | 硬性 | 说明 |
|---|---|---|
| 处理说明 ≥8 字 | 是 | 防止只点“完成” |
| 现场照片达标 | 是 | 电梯困人/燃气/水管爆裂 2 张，其余 1 张 |
| 完工时间已记录 | 是 | 生命周期完整性 |
| 处理内容匹配类型 | 是 | 命中该类型关键词，如水管需含“水/阀/管/积水/压力” |
| 处理时限达标 | 安全类硬性，其余提示 | 安全类超时直接退回；普通类超时记入考核 |
| 燃气安全复检 | 是 | 检漏/浓度/通风/关阀 |
| 困人救援记录 | 是 | 救援/困人/解救/轿厢 + 2 张照片 |

通过：写 `verification_verdict=pass`、`closed_at`，状态 `closed`。  
不通过：写 `verdict=return`、`required_actions`，状态 `returned`，维修工可重新提交完工，再次触发验收。

## 5. 协调器状态机

```
submitted → understood → assigned → accepted → processing → completed
                                  ↘ (人工改派) assigned
completed → closed（验收通过）
completed → returned（验收退回）→ processing（重新提交）
任意在途状态 → 人工改派 → assigned（重置接单/处理时限）
```

- 每次状态迁移写 `ticket_events`，并在 detail 中保存 Agent 输出、置信度、决策日志 ID。
- `run_demo()` 用可注入时钟复现完整故事线：
  - T+00：创建/理解/派单（王建国，30 分钟）；
  - T+25：接单超时提醒；
  - T+26：接单；
  - T+35：处理超时升级主管；
  - T+38：完工但 0 张照片 → 验收退回；
  - T+45：补 2 张照片与完整记录 → 验收通过、闭环。
- 演示工单标记 `is_demo=1`，重复运行会先清理上一条演示工单，避免脏数据。

## 6. 离线分析与数据反哺

`scripts/generate_data.py` 使用固定种子生成 3000 条工单，覆盖 13 类、12 名维修工、5 个小区、180 天，含日内双高峰、月度波动与 12% 超时。`scripts/analyze.py` 计算：

- 总体：闭环率 93.6%、超时率 12.1%、平均处理 92.9 分钟、平均响应 28.9 分钟、满意度 4.50。
- 类型：水管漏水 504 单（16.8%）最高，给排水合计 32.1%。
- 楼栋：6栋 420 单居首，超时率 12.1%。
- 维修工：订单量、平均时长、超时率、满意度、效率指数。
- 时序：月度、近 90 天日趋势、24 小时分布。

输出 `dispatch_priors.json` 供在线 Agent 使用，输出 `analysis_summary.json` 供看板使用，输出 6 张图与约 3300 字中文报告供论文/答辩引用。

## 7. Agent 评估方法

- 样本：3000 条中随机抽取 600 条（`random_state=42`）。
- 标签：历史类型、紧急度、实际责任工种。
- 流程：报修描述 → 理解 Agent → 派单 Agent；验收 Agent 用历史完工记录（说明、照片、时间）重放。
- 指标：类型准确率、紧急度准确率、工种匹配率、综合派单准确率、验收通过率、人工改派率、平均耗时。
- 结果：98.83% / 96.50% / 99.17% / 98.83% / 71.33% / 5.30% / 0.46ms。
- 注意：同分布测试偏乐观；验收通过率低反映历史证据缺失，而非模型错误。

## 8. 数据库与接口

- SQLite 开启 WAL；`tickets/status`、`tickets/created_at`、`agent_logs/ticket_id` 等建有索引。
- 数据访问集中在 `app/repository.py`，Agent 不直接写 SQL。
- REST 契约见 `docs/API契约.md`；核心接口：
  - `POST /api/tickets` 提交并自动理解+派单
  - `POST /api/tickets/{id}/accept|complete|reassign`
  - `POST /api/monitor/scan`
  - `GET /api/tickets/{id}` 返回工单+事件+日志+预警
  - `GET /api/dashboard/summary` 看板聚合
  - `POST /api/demo/run` 一键演示
  - `GET /api/analytics/agent-evaluation` 评估结果

## 9. 前端设计

- 深蓝侧边栏 + 浅灰内容区，主色 `#2563eb`，状态色与 Agent 色统一。
- ECharts 本地加载，无外网依赖，适合答辩现场离线演示。
- 总览：KPI、趋势、类型、楼栋、紧急度、维修工排行、最新工单。
- 工单中心：筛选、表格、详情抽屉、事件时间线、决策日志、接单/完工操作。
- 智能派单：表单、示例、5 节点流水线动画、演示流、候选得分条形图。
- 决策日志：Agent 过滤、置信度、耗时、rationale、JSON 展开。
- 数据分析：6 类图表 + 结论 + 报告入口。
- 架构页：Agent 卡片、数据流、技术栈、创新点、演示流程。

## 10. 测试与可复现性

- `tests/` 29 个测试覆盖理解、派单、监控、验收、演示、API、空数据，以及社区守护与停车收费。
- 数据生成固定种子；演示/监控/验收的时间均可注入，单元测试不依赖当前时间。
- `run.sh` 从零完成环境准备、数据生成、分析、评估、初始化与启动。

## 11. 局限与演进

1. 规则分类对未见过表达泛化有限，可接入轻量 LLM 做兜底并保留规则校验。
2. 监控当前按请求触发，生产环境替换为常驻调度与消息队列。
3. SQLite 单机适合演示，生产应使用 PostgreSQL/MySQL 并增加权限、审计与多租户。
4. 验收照片目前只校验数量，可扩展图像识别（积水、阀门、电梯轿厢）与 OCR。
5. 评估数据为模拟数据，后续可用真实脱敏工单做外部验证。

## 12. v1.1 社区扩展：小区守护与停车收费

### 12.1 小区守护

- 数据表：`residents`（住户档案、标签、在家/外出、最近出门/进门、风险缓存）、`resident_access_events`（门禁出入事件）、`resident_alerts`（未出门预警）。
- Agent：`CommunityGuardAgent`（`app/agents/community.py`）。普通住户阈值 3 天，慢病/行动不便/高龄 2 天，独居老人 1 天；超过阈值按幅度分 L1/L2/L3，并输出未出门天数、风险等级与判定依据。
- 自动巡检：FastAPI lifespan 内启动后台 asyncio 任务，默认每 120 秒调用 `CommunityService.scan()`；页面也提供「立即巡检」。
- 解除机制：登记进门/出门会更新 presence 并自动把该住户未处理预警置为 resolved。
- 隐私边界：模拟门禁事件，不采集摄像头画面；真实部署应采用门磁/门禁脱敏事件并遵守数据合规。

### 12.2 停车收费

- 数据表：`parking_lots`（总车位/费率）、`parking_vehicles`（车牌、月卡、住户）、`parking_sessions`（进出场、时长、费用、缴费）。
- Agent：`ParkingFeeAgent`（`app/agents/community.py`）。规则：30 分钟免费，2 元/小时（不足 1 小时按 1 小时），单日封顶 30 元，有效月卡免费；出场时自动计费，可选择微信/支付宝/现金收费，未缴费保留待缴记录。
- 看板：在场数量/空位/占用率、今日/本月收入、14 日收入趋势、24 小时入场、支付方式、在停车辆与待缴记录。
- 接口：`/api/community/*`、`/api/parking/*`，详见 `docs/API契约-社区扩展.md`。
