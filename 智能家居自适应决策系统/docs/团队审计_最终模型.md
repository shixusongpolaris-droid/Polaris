## 二、High

### H1（high）C4 强制关机绕过仍不完整：策略请求“关机”时会被最小间隔回滚

- 位置：`src/env/simulator.py:697-709`
- 事实：
  - `forced` 分支只在 **请求动作 `ac_idx != 0`** 时执行 `ac_idx=0; forced=True`（`:701-704`）。
  - 如果策略请求 `ac_idx=0`（它自己已经想关机）、而当前 `state.ac_idx>0` 且 `elapsed<min_steps`，C4 分支不执行；随后 `:706-709` 的通用最小间隔检查把 `ac_idx` 回滚为 `state.ac_idx`，空调保持开机。
  - 这与文档“C3/C4 的强制动作不受 C1/C2 间隔约束”冲突（`docs/MDP定义_v1.0.md:439-441`）。
- 复现（`ac_min_switch_interval=60`、`dt=15`、`c4_mode="hard"`、上一步已开、`empty=3`、`step_count=1`、`last_change=0`）：

| 策略请求 | 结果 |
|---|---|
| `ac_idx=0`（想关） | **`ac_idx=1`、`ac_blocked=True`** → C4 失败 |
| `ac_idx=1`（保持开） | `ac_idx=0`、`ac_blocked=True` → C4 成功 |
| `ac_idx=2`（换档） | `ac_idx=0`、`ac_blocked=True` → C4 成功 |

```text
target=0 -> ac_idx=1 blocked=True c3=False
target=1 -> ac_idx=0 blocked=True c3=False
target=2 -> ac_idx=0 blocked=True c3=False
```

- 影响：文档声称“C4 强制关机不受最小切换间隔约束”，但在 `interval>dt` 且策略请求关机时仍可被挡回；任务要求验证的 “interval>60min 绕过是否消失” 答案是 **没有完全消失**。默认 `interval=10<dt=15` 时 `elapsed<min_steps` 不成立，所以默认实验不暴露；一旦按 MDP 计划把 `dt` 细化到 5 分钟，就会暴露。
- 修法：
  ```python
  if force_off and not allow_precool and c4_mode != "off":
      if ac_idx != 0 or self.state.ac_idx != 0:
          ac_idx = 0
          forced = True
          # ac_blocked 可设为 (原请求 ac_idx != 0)，表示“策略想开被强制关”
  ```
  即 **只要当前是开或请求是开，就置 0 并设置 `forced=True`**，让 `:706` 的通用回滚跳过。补测试：`interval=60`、`state.ac_idx=1`、动作 0 → 期望 0；动作 1/2 → 0。

### H2（high）C3 是“步前动作掩码”，不是 16–30°C 状态保证；实测仍到 30.28°C，且不约束通风

- 位置：`src/env/simulator.py:711-726`
- 事实：C3 在每步开始时用 `T_now = self.state.temp_in` 判断，只改 `ac_idx`；它无法阻止本步热增益把温度推过 30°C。实测：
  - 随机策略 2000 步：`temp_in` 最大 **30.28°C**（semi/iid 均如此；检查 2 只查 [-10,60]）；
  - 定向：`T=29.9°C`、15:00、室外约 25°C、动作关空调 → 步后 **30.201°C**，`c3_override=False`（步前 29.9 未触发 C3）。
  - 冷端：`T=16.1°C`、开窗、室外 10°C → 步后 **15.335°C**，`c3_override=False`；C3 只强制关空调，不关闭 `vent_idx`，也不建模制热。当前 10 月室外约 19–25°C，冷端自然发生概率低，但契约上 C3 不是硬区间。
- 影响：`docs/MDP定义_v1.0.md:415` 写“室内温度强制区间 16≤T≤30”，`:435` 写“T>30 强制最低档、T<16 强制关机”。当前实现只保证“步前动作选择”，不保证“步后状态”；30.28 就是实际违约。若团队的 C3 只是 action-level 安全策略，需要改文档并记录 `c3_violation`，不能声称硬区间。
- 修法（二选一）：
  1. **硬区间**：在 `_update_temperature` 后计算 `T_new`，若越界记录 `c3_violation_steps`；要真正避免，需要在步前用“预测 T_next”掩码（例如 `T_now > temp_safe_max - max_step_gain` 时提前强制最低档），或对 `T_new` 做最后钳位并单独计能耗/记录（不推荐静默 clamp）。
  2. **动作级契约**：把 MDP 改成“C3 是动作级安全掩码，不保证 15 分钟步内状态不越界”，并在 `test_env` 用 `c3_violation_steps` 报告 30.28；同时给 `vent_idx` 加冷端掩码（T<16 且室外更冷时关窗）。
- 测试：在 `test_env` 增加“T=29.9/室外 25 步后必须 ≤30”或“记录 violation>0”的断言；当前测试 D 只测 `T=31/15/25` 的步前动作，抓不到这个问题。

## 三、Medium

### M1（medium）启动损耗只覆盖“空调关→开”，不覆盖“空调已开、压缩机从停到启”

- 位置：`src/env/simulator.py:765-766`、`:606-607`、`:782-783`
- 事实：`ac_started = (ac_idx>0 and prev_ac_idx==0 and gross_cooling>1e-9)`。如果上一步 `ac_idx=1` 但 `gross=0`（室温低于设定、压缩机停），本步 `ac_idx=1` 且 `gross>0`（压缩机启），`prev_ac_idx>0`，启动损耗不记、`ac_start_count` 不加。实测 `T0=20` 开 29°C 只收风机 0.010 kWh、start_count=0（符合预期）；但“AC 开着、压缩机循环启动”没有对应测试/计数。
- 影响：`ac_startup_penalty_kwh` 的本意是“压缩机启动损耗”；在 29°C/低负荷附近，AC 常开而压缩机循环时，损耗被漏计。提交说明也承认“瞬时最低功率/循环损耗留待单独标定”，但至少应把“AC 开”与“压缩机启动”拆开。
- 修法：保存 `prev_gross_cooling`/`prev_compressor_on`，定义
  `compressor_started = (gross>1e-9 and (prev_ac_idx==0 or prev_gross<=1e-9))`；
  `ac_start_count` 改名 `ac_on_count`，另加 `compressor_start_count`；补测试“AC 开、gross 0→1”。
- 影响：轻微改变能耗/启动统计；属于 t3/t4 变更，需等复验。

### M2（medium）`ac_min_power_ratio` 已退出环境电量，但脚本仍把它当“可调设备参数”扫描

- 位置：`src/env/simulator.py:578-590` 已不再读取；`src/env/config.py:494-505` 注释说明“不进入平均电量”；但 `scripts/param_sweep_full.py:368`、`scripts/key_experiments.py:300` 仍构造 `RewardConfig(ac_min_power_ratio=...)` 并扫描/画图。
- 事实：`_step_energy_kwh` 对 `ac_min_power_ratio=0/0.2/0.8` 输出完全相同（实测 0.1°C/步时均为 0.023774 kWh/步，p_ac=0.0951 kW），所以这两个脚本的“最低功率敏感性”现在必然全平；`scripts/audit_sim_params.py:78` 仍把它列为参数。
- 影响：如果有人继续用这些脚本，会得到“最低功率不影响结果”的假结论；旧报告中的该参数敏感性也失效。

### M3（medium）`_reset_semi_markov` 的 holiday 概率被 reset 立即推进覆盖

- 位置：`src/env/simulator.py:346-353`（`_reset_semi_markov`）、`:637-640`（`reset` 紧接着 `_update_occupancy`）
- 事实：`_reset_semi_markov` 按 holiday/weekend 概率抽初始 `_sm_occupied`（10:00 节假日 p=0.30，实测 1000 次为 0.31；工作日 p=0.10，实测 0.11）。但 `reset()` 随后调用 `_update_occupancy(...)`，后者立刻 `_advance_semi_markov()`；很多短场景 duration=1，直接翻转状态。实测 reset 完成后初始占用率变成 **节假日 0.612、工作日 0.630**，而不是 0.30/0.10。
- 影响：S9b 在 `_reset_semi_markov` 的 holiday 修复被这一步抵消；所有 semi_markov 回合的初始占用分布都偏“有人”（这是 e9e5bb1 之前就存在的 reset 顺序问题，但 e9e5bb1 改了这里，审计应指出）。会改变回合前几步/首日行为。
- 修法：`reset` 中若 `occupancy_mode=="semi_markov"`，不要调用会推进状态的 `_update_occupancy`；改为按 `_sm_occupied` 直接设置 `occ_a/occ_b/occ_dist`，或让 `_advance_semi_markov` 支持“不推进”的初始化。补测试：节假日 10:00 多次 reset 的初始占用率应≈0.30，工作日≈0.10。
- 影响：改变所有 semi_markov 初始状态；需重跑。

## 四、Low

## 八、结论

- **循环平均**：核心修复成立（p=cooling/COP；`ac_min_power_ratio` 不进入平均电量；启动损耗 gross>0 条件生效），低负荷压缩机 COP=3.0；但“启动损耗按压缩机循环”和“ac_min 参数脚本”仍有残留。
- **C3**：动作层最高优先级、目标档位/关机、`c3_override` 真实覆盖逻辑基本正确；但它是步前 action mask，**不保证 16–30°C 状态区间**（实测 30.28/30.201），且不约束通风；这是 high。
- **C4**：请求开机时强制关机确实不受 interval 约束；但**请求关机时仍会被最小间隔回滚**（interval>dt），这是 high。
- **S9b**：holiday 四处代码一致，action_space.seed 修复有效；但 `_reset_semi_markov` 的初始占用被 reset 推进覆盖（medium），holiday 列表仍不完整（low）。
- **test_env**：A 关闭 C3/C4 合理；B/C 把 C3 单列与文档一致，但没有覆盖 C4 请求关机/interval>dt；D 能抓 C3 未实现，不能抓 C3 状态越界/通风/冲突。7/7 不能作为最终安全约束的充分证据。
