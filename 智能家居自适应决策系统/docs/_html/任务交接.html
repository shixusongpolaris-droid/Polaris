二、五条铁律（违反会浪费时间或出错）

铁律 1：不要用 PowerShell heredoc 跑含中文的 Python

今天因为它浪费了至少 8 次交互。

# ❌ 会静默吞掉引号，且中文引号会破坏字符串
& $py -c @"
print("中文")
"@

正确做法：

  • 短代码：& $py -c "import ast,io; ast.parse(io.open(r'路径',encoding='utf-8').read())"
  • 长代码：写成 .py 文件，用 write 工具写，然后 & $py 文件.py
  • 需要改文件：用 edit 工具，不要用 PowerShell 拼字符串

铁律 2：write 覆盖已有文件前必须先用 read 读过

这是 fs-observation-policy 的要求。报错 file has not been read 就是这个。

新建文件不受限。

铁律 3：.md 文件双击打不开

本机没有关联 .md 程序（assoc .md 报 File association not found）。

给用户看文档时：

& $py "<项目根>\scripts\md2html.py" "<某个.md>"
# 产物在 docs\_html\，双击那个 .html

铁律 4：markdown 链接里不要用 Windows 反斜杠

❌ [文件](D:\path\to\file.md)     ← 反斜杠被当转义符，链接坏掉
✅ [文件](<D:/path/to/file.md>)   ← 用正斜杠 + 尖括号

铁律 5：输出管道不要用 Select-Object -First N 截断后端 Python

会导致假的 [exit code: 1]。要截断就先重定向到文件再读。

五、必须知道的"数字口径"

两个不同的不达标率

口径 含义 用途
总不达标率 所有步（含无人）的越界比例 gen7_unified_protocol.py 的 discomfort
有人不达标率 只统计有人在室的步 主口径，所有结论用它

混用会差 4 个百分点以上。 报告里必须注明用的是哪个。

两个不同的"参照值"

判据 定义 何时用
占优判据（推荐） 参照 = 所有不舒适率不高于 RL 的规则中电费最低者 真实规则点，不插值
插值判据 在相邻前沿点间线性插值 仅在无空档时可用

规则前沿 11.80% ~ 51.73% 有一个 39.9pp 的空档，该区间内禁止插值。

# 缺陷 教训
1 占用判定用子串包含 "在房间" in "不在房间" 子串匹配一律用 startswith

# 错误 偏向
8 4 套规则网格只用 1 套 夸大 RL

十三、几个容易被问住的问题（准备答案）

评委可能问 你怎么答
"为什么 RL 打不过规则？" 单房间、单空调、一阶热动态下，最优策略是阈值型，而规则族能表达阈值。RL 的优势要在高维/未知动力学/多目标耦合中才显现
"你的标定准吗？" RMSE 1.7790，但必须承认 gen5→gen6 只改善 0.17%，参数可辨识性差
"为什么有 7.5pp 说不清的区间？" 10 种子 × 8 回合的检验力不足（MDE 14.2%），要用 45 种子才能分辨
"规则基线是不是你故意做弱的？" 基线被独立审计员补强三次（睡/醒分担、1 小时块、找回丢失的网格），每次都让 RL 更难赢
"结论可靠吗？" 10 轮独立复核，其中 4/4 评估实验逐字节可复现；并且我列出了自己犯过的 11 处错误
"为什么没用 GPU？" 2 万参数的 MLP，瓶颈是 predict() 调度开销（175µs/步）不是算力；实测调线程数只差 14%
"为什么没用闭环控制？" 中央空调无编程接口，这是硬件限制，已如实写入局限

十四、如果一切重来，我会怎么排

  1. 先建环境 + 标定（2 周）—— 这部分做得不错
  2. 同时建立"规则能力上限"作为基线（3 天）—— 我拖到最后才做，导致中间三次误判
  3. 先做单种子探索，但任何结论必须 10 种子 + 审计（这条最重要）
  4. 把"独立审计"从第一天就纳入流程，而不是最后一周
  5. 绝不用"规则基线"当静态对象 —— 它需要和 RL 一样被持续优化
