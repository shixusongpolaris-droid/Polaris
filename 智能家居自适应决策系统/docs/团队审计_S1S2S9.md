## 二、High

### H1（high）C4 默认 `precool` 与 MDP 文档 C4 冲突：默认不满足“无人 30 分钟必须关机”

- 位置：`src/env/config.py:373-374`、`src/env/simulator.py:680-698`、`docs/MDP定义_v1.0.md:416`
- 事实：`ConstraintConfig.c4_mode` 默认是 `"precool"`。当 `force_off=True` 且 `p_arrive_soon >= 0.02` 时，`allow_precool=True`，C4 整段跳过（`simulator.py:682-690`）。在 `empty_steps=2`（恰好 30 分钟）、`p_arrive_soon=0.560` 时，保持空调开机的动作会让 `ac_idx` 保持 >0、`ac_blocked=False`。
- MDP 文档第 416 行仍写“无人超过 30 分钟后，空调必须关闭”，没有 `precool` 例外；`docs/MDP定义_v1.0.md:428-438` 也只讨论 C4 与切换间隔，没有提预冷。默认实验因此不满足文档约束。
- 复现：

```python
# 省略：from src.env import SmartHomeEnv; from src.env.config import SimConfig, ActionConfig
#       from src.env.simulator import encode_action
act = ActionConfig()
env = SmartHomeEnv(sim_cfg=SimConfig(occupancy_mode="semi_markov"), seed=7)
env.reset(seed=7)
# 人为构造：已无人 30 分钟、空调上一步为开
env.sim.state.ac_idx = 1
env.sim._last_ac_change_step = -999
env.sim._empty_steps = 2          # 30 min
env.step(encode_action(1, 0, 0, act))
# 结果：ac_idx=1，ac_blocked=False（默认 precool 允许继续开机）
```

`test_env` 场景 B 只测 `hard`（176/0），场景 C 测 `precool` 并报告 53 步“允许预冷”；默认模式的 C4 是否符合文档没有任何断言。

- 影响：任何“C4 已实现 / 无人 30 分钟关机”的表述只对 `c4_mode="hard"` 成立。在 `occupancy_mode="semi_markov"` 的主实验路径下，默认 `precool` 允许在 30/45/60 分钟三个检查点继续开机（`empty_steps=2..4`，p=0.560/0.764/0.608），直到 75 分钟检查点 p=0 才强制关机；即连续无人开机最长可到约 75 分钟；`iid` 模式因为 `p_arrive=0`，行为等同 hard。
- 建议：
  1. 若实验要声称满足 C4，主实验显式设 `c4_mode="hard"`，或至少同时报告 hard/precool 两套结果与 C4 违反率；
  2. 若保留默认 `precool`，更新 MDP 3.4：把 C4 定义为“30 分钟默认关机；precool 模式下若 p_arrive_soon≥0.02 可放宽到 60 分钟检查点（75 分钟检查点 p=0 时关机）”，并说明它不再是硬约束；
  3. 给默认 `precool` 增加“30–60 分钟仍开机”的显式断言，避免以后把 hard 的 176/0 当成默认行为。

### H2（high）最低压缩机功率只作用于电费、不作用于制冷量：低负荷有效 COP 可低至 0.075

- 位置：`src/env/simulator.py:574-588`（`p_compressor = max(cooling_kw/ac_cop, ac_min_power_ratio*ac_rated_kw)`）；`src/env/config.py:499,512-513`
- 事实：`_update_temperature` 返回的 `gross_cooling` 没有最小值；但 `_step_energy_kwh` 只要 `cooling_kw>1e-9` 就把压缩机功率抬到 `0.20×1.10=0.220 kW`。最低功率对应的制冷量是 `0.220×3.0=0.660 kW`，换算成温度是 `0.660/3.5×2.1175=0.399 °C/步`。因此 `gross_cooling` 在 `(0, 0.399)` 时，模型按 0.220 kW 收费，却只交付了小于 0.660 kW 的冷量。
- 复现（直接调用 `_step_energy_kwh`，取 `dt_h=0.25`）：

| gross_cooling (°C/步) | 对应制冷量 kW | 计费压缩机功率 kW | 有效 COP |
|---:|---:|---:|---:|
| 0.01 | 0.0165 | 0.220 | **0.075** |
| 0.05 | 0.0826 | 0.220 | 0.376 |
| 0.10 | 0.1653 | 0.220 | 0.751 |
| 0.20 | 0.3306 | 0.220 | 1.503 |
| 0.40 | 0.6612 | 0.2204 | **3.000** |

在检查 7 的四个设定温度下，触发最低功率的步数/多收电量（同 seed=42、C4 off、常开）：

| 设定 | 压缩机步数 | 最低功率触发步数 | 多收 kWh/天 |
|---:|---:|---:|---:|
| 23°C | 671 | 162 | 0.339 |
| 25°C | 588 | 222 | 0.983 |
| 27°C | 379 | 147 | 0.475 |
| 29°C | 238 | 154 | 0.638 |

- 影响：25/27/29°C 的部分负荷电费被系统性抬高；`test_env` 检查 7 仍然通过，无法发现这种“收费与交付冷量不一致”。这与 S1 修复要解决的“能耗不随设定温度变化”属于同一类语义问题，只是方向相反。
- 建议二选一：
  1. 若意图是建模“最低运行频率”：在 `_update_temperature` 中把 `cooling` 抬到最小输出 `min_cooling = ac_min_power_ratio*ac_rated_kw*ac_cop/ac_cooling_capacity_kw*ac_max_cooling`（当前 0.399 °C/步），并让温度响应这个最小冷量；
  2. 若意图是建模“启停循环”：去掉 `max(..., ac_min_power_ratio*ac_rated_kw)`，按 `cooling_kw/ac_cop` 计平均功率，用占空比/启动损耗体现最低频率。

无论选哪种，都应补一个“gross_cooling → 电功率 → 交付冷量”的一致性测试。

## 三、Medium

### M1（medium）C4 与最小切换间隔：当 `interval > dt` 时强制关机被“保持现状”回滚；默认配置因 `min_steps<1` 掩盖

- 位置：`src/env/simulator.py:670-703`（尤其 690-703）；`src/env/config.py:350,357`；`docs/MDP定义_v1.0.md:436`
- 事实：默认 `dt=15`、`ac_min_switch_interval=10`，`min_steps=10/15=0.667<1`；`elapsed` 是整数，正常流程下最小为 1，所以第 700 行的“间隔不足则回滚”在当前默认配置下永远不触发，C1/C2 是“天然满足”。但一旦 `interval>dt`（`test_env` 场景 A 就把 interval 设为 60），构造 `previous ac_idx=1`、`empty=3`、`elapsed=1`（上一步刚换过档）、`c4_mode="hard"`：

| 请求 | 实际结果 |
|---|---|
| 请求 `ac_idx=2`（换档） | C4 先置 0，随后第 700 行因 `elapsed<4` 回滚为 1；`ac_idx=1`、`ac_blocked=True` |
| 请求 `ac_idx=1`（保持） | C4 分支不改变（`ac_idx>0` 但 `ac_idx==state.ac_idx`），最终 `ac_idx=1`、`ac_blocked=False` |

即无人超时后的强制关机最多被延迟到 interval 结束，而不是 30 分钟。文档 3.4.1 要求“C4 的强制关机也必须满足最小切换间隔”，所以这是有意取舍；但“延迟”没有被显式建模/报告，且 `hard` 模式在 interval 内无法把已经开着的空调强制关掉（只能等 interval 结束）。
- 影响：默认实验不受影响；MDP 文档明确计划将来把 `dt` 细化到 5 分钟，届时 `min_steps=2`，C4 会延迟 10 分钟，且 `test_env` 场景 B 可能误报。`test_env` 没有“C4 × interval>dt”的回归用例。
- 建议：引入“待执行强制关机”队列，在 interval 满足后的第一步执行；或者明确 C4 优先于 C1/C2（安全约束 override）并同步改 MDP 3.4.1；补 `dt=5` 与 `interval>dt` 的测试。

### M2（medium）启动损耗与 `ac_start_count` 在压缩机未启动时也计入

- 位置：`src/env/simulator.py:741`（`ac_started = (ac_idx > 0 and prev_ac_idx == 0)`）、`599-600`（无条件加 `ac_startup_penalty_kwh`）、`757-758`（`ac_start_count`）
- 事实：`ac_started` 只看空调档位从 0 变为 >0，不看 `gross_cooling`。室温 20°C、设定 29°C、空调从关到开时，`gross_cooling=0`（只送风），但本步能耗为 `0.02 kWh` = 风机 `0.04×0.25=0.01` + 启动损耗 `0.01`，`ac_start_count=1`。
- 复现：

```python
act = ActionConfig()
env.sim.state.temp_in = 20.0
env.sim.state.ac_idx = 0
env.step(encode_action(7, 0, 0, act))   # 29°C 档
# energy_kwh_step = 0.02; gross_cooling = 0; ac_start_count = 1
```

- 影响：注释写的是“压缩机启动损耗/启动次数”，实际统计的是“空调模式从关到开”。在室温已低于设定值时，策略会被收取一次不必要的启动成本，影响“开/关”权衡；29°C 档尤其明显。
- 建议：用 `gross_cooling > 0`（或真实的压缩机启动标志）作为 `ac_started` 条件；`ac_start_count` 改名或改义；补一个“低于设定温度开机”的测试。

### M3（medium）`c4_mode="off"` 并不等于修复前的 C4，旧结果无法按注释复现；且没有 CLI 入口

- 位置：`src/env/config.py:366`（注释“仅用于复现旧结果/对照”）；`src/env/simulator.py:690`；全仓 `c4_mode` 只在 `test_env.py` 被显式设置
- 事实：基线 ce731b5 的 C4 只在 `ac_idx != state.ac_idx` 时检查（动作变化时若无人超时则强制关机）；`off` 是**完全跳过 C4**。因此旧行为在“策略请求换到开机档”时会关机，`off` 不会；`off` 不能复现旧结果。所有训练/评估脚本都不传 `c4_mode`，也没有 `--c4-mode`，想用 `off` 只能改源码/配置。
- 影响：提交说明把 `off` 当作“复现旧结果/对照”的开关，但实际口径不同；旧结果与新结果的对照会混淆。
- 建议：增加 `c4_mode="legacy"`（仅动作变化时检查，等价于 ce731b5），或至少在 `train.py`/评估脚本加 `--c4-mode`；把 `off` 的注释改为“完全禁用 C4，不是旧行为”。

### M4（medium）S9 只改了 `SmartHomeEnv` 的默认日期；`HomeSimulator` 仍是 2026-01-05，且 `reset()` 不恢复时间

- 位置：`src/env/home_env.py:79-82`；`src/env/simulator.py:157`、`607-611`
- 事实：`HomeSimulator()` 的 `sim_time` 默认 `2026-01-05 08:00`；`reset(start_time=None)` 不会重设 `sim_time`。实测：

```text
HomeSimulator() -> 2026-01-05 08:00
sim.reset()     -> 2026-01-05 08:00
sim.step(0)     -> 2026-01-05 08:15
sim.reset()     -> 2026-01-05 08:15   # 时间继续累积
```

`SmartHomeEnv.reset` 每次传 `start_datetime`，所以主路径已修；但 `HomeSimulator` 的 docstring 示例是直接 `sim.reset()`，新增脚本若直接用仿真器会回到 1 月，且重复 reset 时间不归零。
- 影响：S9 的“默认起始日期”只在包装层生效；直接使用仿真器时仍与 10 月室外参数不一致，回合时间也不可复现。
- 建议：给 `HomeSimulator` 设默认 `_default_start = datetime(2026, 10, 12, 0, 0)`；`reset(start_time=None)` 重置为该默认；或把 `start_time` 改为必填/显式报错。

### M5（medium）节假日只“部分生效”：`p_occ_slot` 与 `_reset_semi_markov` 仍按工作日；且占用只加 `weekend_boost`，不切换周末表

- 位置：`src/env/simulator.py:820-828`（`_p_occ_slot`）、`340-353`（`_reset_semi_markov`）、`330-335`（`_occupancy_prob`）、`633/773`（把 holiday 传给 `_update_occupancy`）
- 事实：在 2026-10-01（周四，`holiday_dates` 中）10:00：

```text
obs: is_holiday=1, is_weekend=0, dow=3, p_occ_slot=0.1
_occupancy_prob(10, 3, False)=0.1
_occupancy_prob(10, 3, True)=0.3    # holiday 实际用这个
周六 10:00 的基础概率=0.5             # 节假日并没有用周末行
```

`_p_occ_slot` 只调用 `_is_weekend()`，所以策略在节假日看到的 `p_occ_slot` 是 0.1，而下一步真实占用模型用 0.3。`_reset_semi_markov` 同样只用 `_is_weekend()`，在节假日开始时按工作日概率抽初始状态。另外，提交说明“节假日占用按周末处理”实际只是 `weekday base + weekend_boost`，不是“用周末表”。
- 影响：节假日场景下观测中的历史占用率系统性偏低；初始半马尔可夫状态与随后转移不一致；若论文把节假日当作周末处理，口径不成立。
- 建议：统一 `nonworkday = self._is_weekend() or self._is_holiday()`，在 `_p_occ_slot`、`_reset_semi_markov` 中使用；明确节假日的占用口径是“周末行”还是“weekday+boost”，并写进配置注释/测试。

### M6（medium）`test_env` 新检查的硬编码阈值会在步长/参数变化时误报

- 位置：`scripts/test_env.py:335,362`（`empty0 >= 2`）；`scripts/test_env.py:460`（`e23 - e29 < 1.0`）
- 事实：
  1. C4 阈值实际是 `ac_auto_off_empty / dt_minutes`（`simulator.py:667`），但场景 B/C 写死 `empty0 >= 2`。当前 `dt=15` 时 2 步=30 分钟，恰好正确；若按 MDP 3.4 的计划把 `dt` 改成 5 分钟，C4 要到 6 步才触发，测试在 2 步就要求关机，会**假失败**。
  2. 检查 7 的 `e23 - e29 < 1.0` 不是物理不变量。用 `ac_min_power_ratio=0`、`ac_cop=30` 的参数变体实测：23/25/27/29 = 1.957/1.585/1.305/1.104，单调性成立，但差 0.853 < 1.0，测试会**假失败**。提交本身把 `ac_min_power_ratio` 列为“必须做敏感性分析”的估计值，这一阈值会挡住合法的敏感性配置。
- 影响：未来细化步长或做参数扫描时，测试会给出误导性失败，掩盖真正的回归。
- 建议：用 `int(math.ceil(ac_auto_off_empty / dt_minutes))` 替代 2；检查 7 改成相对比例（如 `E23 > 1.5*E29`）或与基线配置比较，并把阈值/参数显式化；增加 `dt=5` 与低 `ac_min_power_ratio` 的用例。

### M7（medium）`holiday_dates` 是手工 2026 列表，口径不一致且不完整

- 位置：`src/env/config.py:191-197`
- 事实：列表 15 个日期，全部是 2026；其中国庆 10-01~10-07 给 7 天，但春节只给 02-16~02-18 共 3 天，劳动节只有 05-01 一天，清明只有 04-05 一天，端午只有 06-19 一天；没有调休上班日（例如周末被调为工作日的日期），也没有 2027 年。若 `is_holiday` 表示“法定节假日”，国庆不应是 7 天；若表示“连休假期”，其他节日又不完整。
- 复现：`print(SimConfig().holiday_dates)` 可直接看到 15 个日期；对比官方日历即可发现上述口径差异。
- 影响：当前默认评估周 10-12~10-18 不含任何列表日期，主结果不受影响；一旦用 `holiday_dates` 做节假日场景/结论，`is_holiday` 不可信。提交说明也说“只让特征可用”，但未说明数据口径。
- 建议：改用官方日历表（日期 → 是否节假日/是否调休工作日），或明确写“2026 年示例，仅用于代码路径验证”；增加“已知节假日必须为 1、调休工作日必须为 0”的测试。
