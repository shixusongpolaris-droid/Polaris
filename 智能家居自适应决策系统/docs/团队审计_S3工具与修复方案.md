### 1.1 参数解析与全局覆盖：基本正确，但缺少校验

- **`--tags`**（`gen7_tariff_six.py:223-224,236-240`）：`set` 后按 `TARIFFS` 顺序过滤；未知 tag 若与有效 tag 混用会被静默忽略；全部未知返回 2。基本可用。
- **`--seeds`**（`:225,235`）：默认字符串 `"42,66,2026,7,123"`；空串得到 `[]`，随后 `mean([])` 会在规则评估之后抛 `StatisticsError`；重复 seed 不去重。没有启动前校验。
- **`--timesteps`**（`:226,233`）：`int`；0/负数未校验；`model.learn(total_timesteps<=0)` 的行为不应作为实验输入。
- **`--lookahead`**（`:227-228,234`）：`float`；NaN/负数/>1 未校验；`RewardConfig.get_forward_price` 会直接使用该权重，异常值会静默污染奖励。
- **`--suffix`**（`:229-230,242-247`）：非空时改写 `OUT_DIR/OUT/OUT_MD`。没有路径分隔符清洗、没有 `--force`/覆盖确认、没有把 `lookahead/timesteps/tags` 自动编码进目录名。
- **全局覆盖**（`:221` 的 `global TIMESTEPS, LOOKAHEAD_WEIGHT, OUT_DIR, OUT, OUT_MD`）：赋值发生在 `rew_for`/`train_one`/规则评估之前，`rew_for` 使用 `LOOKAHEAD_WEIGHT`（`:111-115`），`train_one` 使用 `TIMESTEPS`/`OUT_DIR`（`:146,150`），主流程使用 `OUT/OUT_MD`（`:353,386`），**覆盖顺序正确**。`SEEDS` 常量（`:88`）已无引用，`--seeds` 默认字符串是硬编码的第二份真值源；修改 `SEEDS` 不会改变 CLI 默认，属于维护隐患（low）。
- **`--tags` 选择与后续循环**：主流程打印/JSON 使用 `selected`（`:257-258,344`），但 md 汇总使用 `TARIFFS`（见 1.2），这是本次最严重的不一致。

### 1.3 high：`--suffix` 为空时单格/消融会覆盖旧六格结果

- 位置：`gen7_tariff_six.py:97-99`（旧路径）与 `:242-249`（只有非空 suffix 才换目录）。
- 复现（路径选择逻辑）：

```text
suffix=''            -> models/gen7_tariff_six/results.json
                        docs/gen7六格电价实验.md
suffix='lookahead0'  -> models/gen7_tariff_six_lookahead0/results.json
                        docs/gen7六格电价实验_lookahead0.md
```

- 风险场景：
  - `--tags t1_tou` 不带 `--suffix`：`all_out` 只有 t1_tou，最终 `json.dump` 到旧 `models/gen7_tariff_six/results.json`，旧六格结果被单格结果覆盖；md 还会因 1.2 先崩（但 JSON 写入在崩溃前，仍会覆盖）。
  - `--lookahead 0` 不带 `--suffix`：即使跑全六格，也会把旧 0.6 结果覆盖成 0.0 结果。
  - 同一 `--suffix` 重跑（例如把 0.6 也写成 `lookahead0`）：覆盖前一次新结果；没有 `--force` 保护。

- 建议：
  - 当 `len(selected) < len(TARIFFS)` 且 `args.suffix == ""` 时，`parser.error("--suffix is required when --tags selects a subset")`；
  - 当 `--lookahead != 0.6` 或 `--timesteps != 300_000` 且 suffix 为空时同样要求 suffix；
  - 或自动生成 `subset_<tags>_la<lookahead>_ts<timesteps>`；
  - 若目标 `results.json` 已存在且无 `--force`，拒绝写入并提示备份；
  - 当前正在跑的 `lookahead0` 不用改；以后重跑 0.6 请用 `la06` 或 `base` 等不同 suffix。

### 1.4 medium：`valley_share` 的计算口径

- 位置：`gen7_tariff_six.py:159-208`，关键 `:167-169,177,191-194,201`。
- 代码每步：

```python
e = float(info["components"]["energy_kwh"])   # 刚执行步（起点小时）的电量
cost += info["components"]["elec_price"] * e  # 旧口径：步后 obs 的 elec_price

    e_valley += e
```

- 与旧口径的关系：旧 `gen7_unified_protocol.measure` 也是 `hour = int(od["hour"])`（步后）且 `cost += info["components"]["elec_price"]*e`；`RewardCalculator` 用步后观测定价。**因此 `valley_share` 与旧 `cost` 的口径一致**，S3 内部（0.6 vs 0.0）比较是可比的。

```text

post-step hour: 22.0; elec_price: 0.307; price_tier: valley
start price: 0.617; post price: 0.307
```

- 影响：
  - `cost` 在 22:00/06:00 边界把峰/谷电价错配一步；旧结果已有此性质，S3 若只做同脚本对比，偏差相互抵消；
  - `valley_share` 作为新指标，绝对值会受 2 个边界步/天影响（约 1–2% 电量；若边界步电量高则更多）。
- 建议：
  1. 若只做 S3 对照，保留旧 `cost`，另加 `cost_hour_aligned` 与 `valley_share_hour_aligned`（在 `env.step` 前取 `hour0 = int(env.sim.sim_time.hour)`，用 `rc.get_price(hour0)`/`get_tier_name(hour0)`），md 中明确使用哪一种；

## 二、High 修复方案（不实施，只给方案）

### H1（对应 `docs/团队审计_S1S2S9.md:38-60`）C4 默认 `precool` 与 MDP 冲突

**问题回顾**：`ConstraintConfig.c4_mode` 默认 `"precool"`；`semi_markov` 下 `empty_steps=2..4`（30/45/60 分钟）且 `p_arrive>=0.02` 时 C4 跳过，75 分钟检查点 p=0 才关机；MDP 第 416 行仍写“无人超过 30 分钟必须关闭”。

**三种路线对比**

| 路线 | 改动 | 结果影响 | 评价 |
|---|---|---|---|
| A. 只改文档 | `docs/MDP定义_v1.0.md:416,428-438` | 无 | 必须做；但不解决“默认行为与硬约束同名”的歧义 |
| B. 默认改 `hard` | `src/env/config.py:373` | **改变 t3 `new`、t4 heldout、t1_tou 重跑** | 会让 C4 严格成立，但禁掉 gen7 的“预测回家预冷”；不推荐现在做 |
| C. 加 CLI/消融 + 文档 | 训练/评估脚本加 `--c4-mode`，结果 JSON 记录；默认仍 `precool` | 默认无影响；hard 消融产生新结果 | **推荐**：不改现有 t3/t4，又能让读者看到两种口径 |

**推荐方案（C + A）**

1. **文档先行**：把 C4 定义为两种模式，而不是一个绝对句：
   - `hard`：无人≥30 分钟强制关机，禁止再开机；

### H2（对应 `docs/团队审计_S1S2S9.md:62-90`）最低压缩机功率只计电费、不抬升冷量

**问题回顾**：`p_compressor=max(cooling_kw/COP, 0.20×1.10)`，但 `_update_temperature` 的 `cooling` 没有下限；`gross=0.1` 时计费 0.220 kW、交付 0.165 kW，有效 COP 0.751；`gross=0.01` 时 0.075；`gross≥0.399` 才回到 COP=3。

**三种方案取舍**

| 方案 | 做法 | 优点 | 缺点 | 结果影响 |
|---|---|---|---|---|
| **1. 循环平均功率（推荐）** | 去掉 `max(..., min_power)`；`p_compressor = cooling_kw/COP`；用 `ac_startup_penalty_kwh`/新增 `ac_cycle_penalty_kwh` 体现启停损失 | 与热模型能量守恒；不人为过冷；低负荷平均功率与实测 290–330 W 量级更一致；实现小 | 不再显式出现“最低功率”项；需要启停/循环参数 | 能耗下降（见下）；所有 t3/t4 需重跑 |
| 2. 最低制冷量 | 若 `ac_idx>0` 且 demand>0，`cooling=max(cooling, min_cooling)`，其中 `min_cooling=min_power*COP/capacity*ac_max_cooling≈0.399°C/步`；仍按 floor 计费 | 计费与交付冷量一致；保留“最低频率”语义 | 会过冷、改变温度轨迹/舒适度；与真实“达到温度后停压缩机/循环”不符；对前沿影响更大 | 温度与能耗都变；需重跑 |
| 3. 只移除底价 | 删除 `max(..., min_power)`，无循环损耗 | 最小改动；能量守恒 | 低估部分负荷的启停损失；29°C/低负荷会偏乐观 | 能耗下降；需重跑；仅宜作敏感性 |

**推荐：方案 1**。理由：
- 当前热模型是 15 分钟单区连续模型，真实变频机在低负荷会 cycling，**平均电功率 = 平均制冷量/COP** 是能量守恒的正确口径；最低频率应该体现在“最小输出 + 占空比 + 启停损耗”，而不是“瞬时收费 floor”。
- 方案 2 把最低输出强行注入温度方程，会让房间被过冷（`gross` 被抬到 0.399°C/步），这比“少收一点电费”对舒适度/前沿的扭曲更大。
- 方案 3 是方案 1 的简化版；如果没有 cycling 参数，可先上线方案 1 并保留 `ac_min_power_ratio` 仅用于诊断/敏感性，但要在文档中说明“不再直接计费”。

**改动点（方案 1）**：
- `src/env/simulator.py:577-588`：压缩机功率改为 `cooling_kw/max(ac_cop,1e-6)`；`p_ac = p_compressor + ac_fan_kw`；不再 `max(..., min_power)`。
- `src/env/config.py:486-513`：更新 `ac_min_power_ratio` 注释（改为“用于推导最小输出/循环诊断，不直接作为计费 floor”）；可新增 `ac_cycle_penalty_kwh` 或复用 `ac_startup_penalty_kwh`。
- `src/env/simulator.py:741`：启动损耗条件改为 `gross_cooling>0`（见低风险项），使“循环”只在压缩机真正启动时计损。
- `scripts/test_env.py:422-468`：检查 7 改为“单调 + 绝对量级 + gross→电功率一致性”。
- 文档：`docs/MDP定义_v1.0.md:312` 补“风机/最低功率/循环”的口径。

**测试**：
1. `_step_energy_kwh(1,0,0,gross)` 表：gross=0 时 `p_ac=fan`；gross=0.1 时 `p_comp≈0.055`（不是 0.22），有效 COP≈3；gross=2.1175 时 `p_comp=min(1.167,1.1)=1.1`（或先解决 L6 的 3.5/3>1.1 口径）。
2. 检查 7：`E23>E25>E27>E29` 且 `E23-E29` 合理；再断言 `E25` 平均 AC 功率落在可解释区间（如 0.2–0.5 kW），防止“单调但整体 2 倍”。
3. 能量恒等式：对一系列 gross，`p_comp*dt` 与 `gross/ac_max_cooling*capacity/COP*dt` 一致（允许 cap）。
4. 若加循环损耗：构造低负荷长驻留，比较有/无 cycle penalty 的能耗差，确认量级合理。

**影响数字（方案 1 参考）**：把 floor 设为 0（等价纯平均）时，同一 seed/回合的 23/25/27/29°C 日均从当前 11.248/8.177/4.871/3.024 变为约 10.910/7.194/4.396/2.386（−3%/−12%/−10%/−21%）；再加循环损耗会回补一部分。具体数值需重跑确认。

**对 t3/t4 的影响**：**全部改变**（t3 `new/new_off`、t4 heldout；t1_tou 重跑）；必须等 t3/t4 完成。

### H4（对应 `docs/团队审计_S1S2S9.md:114-120`）C3 未实现

**问题回顾**：`ConstraintConfig.temp_safe_min/max`（`src/env/config.py:352-354`）只存在于配置；`simulator.py:650-703` 没有读取；`test_env` 随机策略 2000 步室温可达 30.90–31.07°C；MDP 第 415 行仍称 C3 已实现。

**推荐动作掩码逻辑（C3 优先级最高）**：

```python
# 在 C4/最小切换之前或之后均可，但 C3 必须最后覆盖（安全优先）
T = self.state.temp_in
c3_override = 0
if T > cfg.temp_safe_max:                 # 31°C
    ac_idx = 1                            # 最低设定档（23°C），强制制冷
    if self._temp_out < T:                # 室外更凉才开窗
        vent_idx = 1
    c3_override = +1
elif T < cfg.temp_safe_min:               # 15°C（无制热模型）
    ac_idx = 0
    vent_idx = 0
    c3_override = -1
```

- **优先级**：C3（安全）> C4（无人关机）> C1/C2（最小切换）。若 C3 与 C4 冲突（无人但过热），C3 开空调并记录 `c4_violation`；若 C3 与 C1/C2 冲突，安全 override 并记录 `interval_override`。
- **冷端限制**：项目没有制热动作，T<16 时只能关空调/关窗，靠环境得热回升；需在文档明确“C3 冷端是 best-effort，不保证立即回到 16°C”，或者增加制热动作（超出当前范围）。
- **观测/信息**：`info["c3_override"]`、`metrics["c3_override_count"]`、`c3_violation_steps`；C3 不能只做“动作掩码”就声称状态一定在区间内——若容量不足（例如 31°C 且空调已 23°C 仍降不下来），要记录 violation，不能偷偷 clamp `temp_in`。
- **配置**：可加 `c3_mode: str = "mask"`（`mask/off`），`off` 仅用于复现旧结果；`temp_safe_min/max` 保持。
- **不要**在 `_update_temperature` 里直接把 `T_new` clamp 到 16–30：那会同时丢失能量/物理一致性，只适合作为最后的安全钳位并单独记录。

**测试用例**：
1. `temp_in=31`、`c4_mode=off`、动作 `ac_idx=0` → 结果 `ac_idx=1`，`c3_override=+1`。
2. `temp_in=15`、动作 `ac_idx=1` → 结果 `ac_idx=0`，`c3_override=-1`。
3. `temp_in=31`、`empty_steps>=2`、`c4_mode=hard`、动作 0 → C3 胜出，AC 开；`info` 同时记录 C4 冲突。
4. `temp_in=31`、`ac_min_switch_interval=60`、刚切换 → C3 仍 override，记录 interval override。
5. 2000 步随机策略（固定 action_space seed）：断言 `temp_in ∈ [16,30]`，或记录 violation 率；若容量不足导致越界，测试应报告而不是静默通过。
6. `test_env` 的检查 5 增加 C3 场景；检查 2 的 31°C 越界应变成失败（或明确 warning）。

**对 t3/t4 的影响**：C3 改变动作/温度轨迹，**影响 t3 `new/new_off`、t4 heldout、t1_tou**；必须等 t3/t4 完成并重跑。若暂时不能重跑，可先加 `c3_mode="off"` 默认保留旧行为，但 MDP 的“C3 已实现”必须改为“可启用/未启用”，不能声称默认合规。
