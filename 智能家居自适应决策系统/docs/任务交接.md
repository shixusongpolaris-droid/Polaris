# 二、五条铁律（违反会浪费时间或出错）

## 铁律 1：不要用 PowerShell heredoc 跑含中文的 Python

**今天因为它浪费了至少 8 次交互。**

```powershell
# ❌ 会静默吞掉引号，且中文引号会破坏字符串
& $py -c @"
print("中文")
"@
```

**正确做法**：
- 短代码：`& $py -c "import ast,io; ast.parse(io.open(r'路径',encoding='utf-8').read())"`
- 长代码：**写成 .py 文件，用 `write` 工具写，然后 `& $py 文件.py`**
- 需要改文件：**用 `edit` 工具，不要用 PowerShell 拼字符串**

## 铁律 2：`write` 覆盖已有文件前必须先用 `read` 读过

这是 fs-observation-policy 的要求。报错 `file has not been read` 就是这个。

**新建文件不受限。**

## 铁律 3：`.md` 文件双击打不开

**本机没有关联 .md 程序**（`assoc .md` 报 File association not found）。

**给用户看文档时**：
```powershell
& $py "<项目根>\scripts\md2html.py" "<某个.md>"
# 产物在 docs\_html\，双击那个 .html
```

## 铁律 4：markdown 链接里不要用 Windows 反斜杠

```markdown
❌ [文件](D:\path\to\file.md)     ← 反斜杠被当转义符，链接坏掉
✅ [文件](<D:/path/to/file.md>)   ← 用正斜杠 + 尖括号
```

## 铁律 5：输出管道不要用 `Select-Object -First N` 截断后端 Python

**会导致假的 `[exit code: 1]`**。要截断就先重定向到文件再读。

# 五、必须知道的"数字口径"

## 两个不同的不达标率

| 口径 | 含义 | 用途 |
|---|---|---|
| **总不达标率** | 所有步（含无人）的越界比例 | `gen7_unified_protocol.py` 的 `discomfort` |
| **有人不达标率** | 只统计有人在室的步 | **主口径**，所有结论用它 |

**混用会差 4 个百分点以上。** 报告里必须注明用的是哪个。

## 两个不同的"参照值"

| 判据 | 定义 | 何时用 |
|---|---|---|
| **占优判据**（推荐）| 参照 = 所有不舒适率不高于 RL 的规则中电费最低者 | 真实规则点，不插值 |
| **插值判据** | 在相邻前沿点间线性插值 | 仅在无空档时可用 |

**规则前沿 11.80% ~ 51.73% 有一个 39.9pp 的空档，该区间内禁止插值。**

## 如果将来 push 失败

| 症状 | 原因 | 解法 |
|---|---|---|
| 提示输入密码 / 挂在 22 端口 | `~/.ssh/config` 丢了 | 重建上面那份 config |
| `Permission denied (publickey)` | 密钥被删 或 GitHub 上公钥被移除 | 在 GitHub Settings → SSH keys 重新添加上面那串公钥 |
| `Host key verification failed` | known_hosts 被清 | 加 `-o StrictHostKeyChecking=accept-new` |
| 提示密码短语 | 密钥被替换成带 passphrase 的 | 让用户输一次，或生成新的无密码密钥 |
| 需要用户授权 | **本仓库不会出现**（SSH 密钥已配置）| — |

## ⚠️ 关于用户说的"需要授权"

用户记忆中的"授权"可能指两种情况，**都不是本仓库**：

1. **HTTPS 方式**（用 `credential.helper=manager`）—— 会弹 Windows 凭据窗口
2. **DSH 的沙箱升级授权** —— 那是文件访问权限，与 git 无关

**本仓库用 SSH + 无密码密钥，两者都不涉及。**

# 十六、六格电价实验的结论（2026-10-19 23:40 补）

**这一轮之后才有，交接时还没有。**

## 结果（t11 独立复评：30/30 模型逐位一致）

| 配置 | 档位 | 计费 | RL 电费±CI | 规则参照 | 差值 | p | 判定 |
|---|---|---|---|---|---|---|---|
| t1_flat | 1 | 未分时 | 1.756±0.134 | 2.044 | **−14.1%** | 0.0039 | ✅ RL |
| t1_tou | 1 | 分时 | 2.064±0.246 | 1.916 | +7.7% | 0.170 | ❌ |
| t2_flat | 2 | 未分时 | 2.232±0.357 | 2.209 | +1.0% | 0.872 | ❌ 持平 |
| t2_tou | 2 | 分时 | 2.156±0.406 | 2.102 | +2.6% | 0.729 | ❌ 持平 |
| t3_flat | 3 | 未分时 | 2.365±0.239 | 2.916 | **−18.9%** | 0.0031 | ✅ RL |
| t3_tou | 3 | 分时 | 2.719±0.692 | 2.950 | −7.8% | 0.407 | ❌ |

## ⭐ 最有价值的发现

**RL 学会了对电价信号做出反应（移峰填谷成功），但方式是"过度预冷"：**

```
谷段用电占比  6.18% → 18.71%   (+12.53pp, p=0.018)   ← 移谷成功
平均电价      0.617 → 0.557    (−9.7%)                ← 电价降了
总电量        +30.1%                                  ← 但多用了 30% 电
净电费        +17.5%                                  ← 结果更贵
```

**交互效应是真实的**：diff-in-diff = +21.80pp [6.59, 37.02]，t=3.98，p=0.016，
n=5 功效 84%。

## 正确表述（**不要说"电价越高 RL 越好"**）

> 电价结构对 RL—规则对比有**非单调**影响。
> 分时电价在第一档暴露 RL 的"过度预冷"缺陷（能耗 +30%、净电费 +17.5%），
> **规则更擅长利用 TOU**；高电价（第三档未分时）下 RL 显著省 18.9%。

## 可信度分层

| 结论 | 强度 |
|---|---|
| t1_flat RL 省 14.1% / t3_flat RL 省 18.9% | ✅ 5/5 种子显著 |
| t1 的 flat→TOU 交互（21.8pp）| ✅ p=0.016 |
| t2 两格持平 | ✅ 无显著差异 |
| t1_tou 规则省 7.7% | ⚠️ 单独不显著（需 ~17 种子）|
| t3_tou RL 省 7.8% | ⚠️ 单独不显著（需 ~48 种子，seed42 异常）|

## 局限

5 种子、单周（9100–9107）、`energy_scale=30` 固定、
`t3_tou` 的 seed42 是异常点（4.464 kWh / 3.579 元，其余种子 2.31~2.97）。

# 十八、给下一个我的最后三段话

## 第一段：关于结论

**这个项目最终得出的不是一个"赢了"的结论，而是一条边界。**

规则在极舒适端更好，强化学习在中高不舒适端更好，中间一大段分辨不出。
这在单房间、单空调、一阶热动力学的设定下是合理的 —— **最优策略本来就是阈值型**。

**如果你将来想让它变成"RL 更优"的结论，正确的做法不是继续调参，
而是换一个 RL 真的有结构性优势的问题**：多房间耦合、占用不确定性、
未知动力学、或者多设备协同。**不要靠弱化基线来制造胜利。**

## 第二段：关于我自己

**我被审计抓出 4 处分析错误，其中 3 处都让 RL 显得比实际更强。**

这不是运气问题，是一种系统性的乐观偏向。**你要警惕自己也有。**

具体的自检方法：
1. 每次得出"某方法更好"的结论前，问：**我的基线是独立构造的吗？**
2. 每次得出"某方法无效"的结论前，问：**我的样本量够检出这个效应吗？**
3. 每次得出"某区间无解"的结论前，问：**是我搜索空间不够，还是真的无解？**

## 第三段：关于用户

**这个用户判断力很强，问的问题都很准。**
它抓出的 4 个问题里，有 3 个是"你没让我做该做的事"这类根本性质疑，
而不是表面的数字错误。

**它要求的"确切且客观的评价、不要刻意迎合"是真心的** ——
每次我如实报告不利结果，它都表示感谢。

**所以：不要为了让它高兴而美化数字。**
