```
谷 [23, 24, 25] × 平 [25,26,27] × 峰 [27,28,29] × 预冷 [0,1,2] × 无人时 [关机,不停机] = 216 组
```

`3 × 3 × 3 × 3 × 2 = 162 ≠ 216`。真实代码（`:204`）是 `V = [23.0, 24.0, 25.0, 26.0]`（4 个谷值），`4×3×3×3×2 = 216` 才对。只有控制台打印（`:196-198`）用了正确的 4 个值。也就是说：**本次修改把总数改对了，却把"和自己列出的网格乘不起来"这个新矛盾留在了 docstring 和最终报告里**（`docs/规则能力上限.md:5` 已实测仍是 `谷 [23,24,25]`）。docstring 的旧注释 `v_sp ∈ {23, 24, 25}` 属于上一代网格，本次没跟着改。

### 4.3 附带发现：230 次评估只有 62 种不同行为（中）

对 `results.json` 做行为等价分组（energy/cost/discomfort 全等去重）：

```
不同行为数 = 62 / 总组数 = 230
含重复的行为组 = 48，重复浪费的评估 = 168
分时族 (v,p,precool,keep) 组合数 = 72，其中 f 造成结果差异的组合数 = 0
分时族实际独立行为数 = 48 / 216
```

原因有两个，都是既有设计、但让"230 组能力上限"这个说法名不副实：

1. **平段设定温度 `f` 完全无效**：`rule_ceiling.py` 的 `evaluate()` 用默认电价（`price_valley=0.307, price_flat=0.617, price_peak=0.617`），`get_tier_name()` 永远不会返回 `"flat"`；`make_rule()` 里 `target = f_sp` 只在既非谷也非峰时才用到，所以 `f ∈ {25,26,27}` 三份结果逐位相同（实测差异组合数 = 0）。
2. **`v=23` 时 `precool` 也无效**：`clampi(target, lo=23.0)` 把 `23 − precool` 全截回 23，所以 `precool=0/1/2` 三份相同。

所以 230 这个数字**是循环次数**，不是有效搜索规模；真正不同的规则只有 62 条。这不影响"跑了几组"的计数，但"我们把规则族做到了 230 组的能力上限"这句话在报告里会误导读者。

### 4.4 结论

**230 属实（通过前半），但网格枚举与 216 自相矛盾（未通过后半），有效网格仅 62 种行为。**

```
cooling = -dT - ua·(T-T_out) + gain_base + solar_coef·solar_factor + gain_occ·occ
```
