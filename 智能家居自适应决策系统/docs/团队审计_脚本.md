### D-1【高】`tariff_cross_eval.py` 的恒温器仍返回裸档位 2/1

```python
# scripts/tariff_cross_eval.py:113-119
def _thermostat(env, target, deadband=0.5):
    T = env.sim.state.temp_in
    if T > target + deadband:
        return 2      # 制冷
    if T < target - deadband:
        return 0      # 关闭
    return 1          # 维持
```

当前 `ac_setpoints = [23,24,25,26,27,28,29]`，所以：`return 2 → 24°C`、`return 1 → 23°C`。而三个基线都声明是 **25°C**：

```python
# scripts/tariff_cross_eval.py:122-138
def policy_always_ac(env):
    return encode_action(_thermostat(env, 25.0), 0, 0, env.act_cfg)   # 标签"全程开空调25°C"
```

即"25°C 基线"实际是：过热→24°C、滞环内→**23°C**。这既不是原来那个"过热反而升温"的已知缺陷，也不是正确实现，而是**换了方向的同源错误**（错误的档位字面量）。

**已量化确认**：`models/tariff_cross_eval/summary.json` 里三条基线的实测结果是

```
base_always   energy=4.650 kWh/天  cost(flat_t1)=2.869  discomfort=24.6%
base_occ      energy=3.187        cost=1.967           discomfort=25.2%
base_rule     energy=3.398        cost=2.097           discomfort=25.2%

```

`scripts/validate_calibration.py:61-72, 115-117` 是同类问题：
```python

...

if solar: gain = cfg.internal_gain + 0.33 * cfg.ua_coef   # 用 0.33·ua 手搓日照项
```

### O-4【高】"每种电价下的最优策略"表把三条基线整行漏掉了，结论反转

```python
# scripts/tariff_cross_eval.py:296-305
for t in TARIFFS:
    best = None
    for p in policies:
        if not p.get("trained_on"):      # ← 基线没有 trained_on，被整条跳过
            continue
        r = results[p["key"]]["by_tariff"][t["key"]]
        if best is None or r["cost"][0] < best[1]:
            best = (p["label"], r["cost"][0], r["discomfort"][0])
```

`policies` 里明明有 9 个策略（3 基线 + 6 PPO），但这段筛选把 3 条基线全部排除，表头却写"每种电价下的最优策略"。实测后果（`docs/上海电价交叉评估.md:56-65` 与 `models/tariff_cross_eval/summary.json` 对照）：

| 电价 | 文档写的"最优" | 实际全候选集最优 |
|---|---|---|
| 分时·1档 | PPO(未分时·3档训练) 2.939 元/天 | **base_occ 1.435 元/天** |
| 未分时·1档 | PPO(未分时·3档训练) 3.254 元/天 | **base_occ 1.967 元/天** |
| 分时·3档 | PPO(未分时·3档训练) 4.654 元/天 | **base_occ 2.274 元/天** |

即文档给出的"最优策略"比真实最优贵 **1.0–2.8 元/天（约 2 倍）**，方向完全反了。同一份文档第一节也只列 PPO（因为同样按 `trained_on` 过滤），读者看不到任何基线数字。

补一句公允说明：基线便宜是因为它牺牲了舒适度（`base_occ` 不达标 25.2% vs PPO 7.1%），所以"谁最优"本质上需要等舒适度口径（`tou_equal_comfort.py` / `multiseed_equal_comfort.py` 做的就是这件事）。但本表的表头写的是"按电费"，按字面就应是基线胜出；把基线整行隐去的做法既不符合表头，也让读者无法自行做这个权衡。

修复：`best` 循环去掉 `trained_on` 过滤（用 `p["key"]` 取 `by_tariff` 即可），并在第一节补上基线行；或在表头明确写"仅 PPO 候选中"。

## 10. 需要在重跑/人工确认后才能定性的项（不硬下结论）

1. **`docs/空调制冷能力标定.md`（ac_coef=2.000, ac_max=1.30）与当前配置（2.0125 / 2.1475）的关系**：文档生成于 10-17 00:38，早于 config 里"全时段联合标定"的修订。按 D-8 的分析，该文档的拟合公式已过期；但当前配置里的 2.0125/2.1475 注明来自"全时段联合标定（每小时 7.53/12.67）"，与本文档的 1.30 不是同一次拟合。**需要确认哪个数值才是最终采用值**，以及是否要用修正后的五项式重跑 `calibrate_ac_cooling.py`。
2. **`verify_doc_numbers.py` 的 9 处不符**：无法从静态代码判断是文档过期还是结果文件被覆盖。建议用结果文件的 mtime + 训练参数（`train_result.json` 里的 `config`）反查生成顺序。
3. **`docs/上海电价交叉评估.md` 的具体数值**：D-1 已能确认基线长期停在 23°C（`base_always` 不达标 24.6% 即指纹），但"正确的 25°C 基线"考多少电费，必须重跑才能给数；O-4 的"最优策略反转"结论不依赖这个重跑（1.435 vs 2.939 的差距远超基线错位幅度）。

5. `test_env.py` 观测越界（O-1）对已训练模型的实际影响：当前 SB3 不裁剪观测，故训练/评估行为未受影响；但若结论依赖"观测在声明范围内"，则该前提已被证伪（353 次越界/2000 步）。
